# Search overhaul

## Why

A brother (living3water@gmail.com, 2026-10-22, "Search all lyrics") asked for an exact phrase search without
duplicates, the All Lyrics tab closer to the front, and a way to search only some books (e.g. New Songs). Lemuel
answered 2026-10-23 that a unified search is planned. Today's search makes the user guess where a word is (First
Lines, Subjects, Authors, All Lyrics or Music) before searching, and:

- **All Lyrics lists stanzas, not hymns**: a hymn shows once per matching stanza, and again in every book with the
  same words.
- **No exact phrase**: every word is matched on its own, in any order; quotes are removed (`QueryBuilder.addFilter`).
- **All Lyrics ignores hidden books** (Settings → hymn books): the stanza query has no book filter (`HymnsDao.getByLyricText`).
- **Case and accents**: SQLite `LIKE` ignores case only for A–Z. "бог" does not find "Бог" (Russian), "jesus" does not
  find "Jésus" (French, Spanish, German...).

The web app already has a unified search (`tools/web/src/db.js` `search()`, one `search` table built by `build.py`).
Android can follow it, and the two stay alike.

## The rule that must not break: number lookup in the meetings

The most common use: a hymn is called out, the saint taps Search and types the number. So, exactly as today:

- Search opens on **Hymn Numbers**, always (no "remember the last tab": a lyrics search last time would bring up the
  text keyboard in the next meeting).
- The **number keypad** comes up at once.
- Typing filters live; **Enter opens `<current book><number>`**.

## The new tabs

| Tab | Keyboard | Empty box | Typing |
|---|---|---|---|
| **Hymn Numbers** (first, default) | number keypad | the current book by number | as today |
| **Search** (new, second) | text | browse the current book (see below) | one list of hymns from everything |
| **Favorites** | none | as today (with Back up / Restore) | not searchable |
| **History** | none | as today | not searchable |

First Lines, Subjects, Authors, All Lyrics and Music go away as tabs; their searching moves into Search, their browsing
into Search's empty state. (When the box gets focus on Favorites or History, jump to Search, as it jumps to First
Lines today.)

### Search, typing

- **One row per hymn**: `<ID> - <first line>`, the book icon, and when the first line is not what matched, one more
  line showing why: the stanza line with the words (as the web app's `matchLine`), or `Author: …`, `Subject: …`,
  `Key: G · Tune: …`. Matched words highlighted.
- **Words match anywhere** in: first stanza line, first chorus line, subject (main and sub category), author and
  composer, key and tune, all stanzas. Every word must be found (any order, parts of words count: "bless" finds
  "blessing"). One-letter and two-letter words are no longer dropped (the normalized text makes them cheap).
- **Exact phrase**: text in quotes ("ancient of days") must appear as it is, words together, in one field.
- **Ignore case and accents** in every alphabet (normalized text, below).
- **Order**, best first (the web app's scores, extended):
  1. first line starts with the phrase
  2. first line has the phrase
  3. chorus line has the phrase
  4. all words in the first line, then in the chorus line
  5. subject, then author/composer, then key/tune match
  6. the words together in a stanza, then as whole words, then as parts of words ("flow" before "flowers")
  7. ties: current book first, then the book order of the drawer, then the number
- **Books**: a two-way switch above the list, like the web app: **`<current book> (n)`** | **`All books (n)`**. Starts
  on the current book; if it has nothing, All books. Hidden books are always left out. To search only New Songs: open
  a New Songs hymn, then Search (or see the open question on a book picker).
- **Only digits typed** ("123"): first row is "Go to `<current book>123`", Enter opens it, as on Hymn Numbers. A hymn ID
  ("NS 151", "e8") also goes straight there (the web app's `parseQuery`).
- Live as you type, with a short delay (~150 ms) so fast typing doesn't run a query per letter.

### Search, empty box (browsing)

A row of chips, current book only:
- **First Lines** (default): first stanza and chorus lines A→Z, as the First Lines tab today.
- **Subjects**: by main category, then sub category.
- **Authors**: by author, then composer.
- **Tunes**: hymns with key and tune, by tune (the Music tab today).

So nothing that can be browsed today is lost. (Today these lists show all books; current book only makes them shorter
and matches the empty Hymn Numbers tab. See open questions.)

## How: a search table

One row per hymn, all text in **search form** (the web app's `norm()`: no markup, accents removed, lower case, final
sigma → sigma, only letters, marks and digits, single spaces; the marks keep Tamil and Burmese vowel signs):

```
search(id TEXT PRIMARY KEY, grp TEXT, first TEXT, chorus TEXT, subject TEXT, people TEXT, music TEXT, body TEXT)
```

`body` is all of the hymn's own stanzas joined with ` | `. The query is the same normalization of what was typed, then
`LIKE '%word%'` per word (`instr` works too), score and sort in Java. Measured on the current database (15,938 hymns,
81,894 stanzas, 11 MB of lyrics) on the PC: 8–15 ms per query, the same as today's All Lyrics query. A phone may be
5–10 times slower: still fine for live search with the delay.

**Where the table is built** (open question 1):
- **A. At provisioning** (in `hymns.sqlite`, like the web app): simplest, one normalizer (Python) for both apps. But the
  database grows from 22.9 MB to 41.1 MB (+4.7 MB compressed, so the download grows by about that), and the phone keeps
  it twice (inside the app and the copied database).
- **B. On the phone**, right after the app copies the database (it does that on every update, `HymnsSqliteHelper`):
  no bigger download, +18 MB only in the copied database. Costs a Java normalizer that must give exactly what the
  Python and JS ones give (one shared test file of samples for all three), and a few seconds once per update in the
  background (Search shows "Preparing search…" and uses the old slow query until then). To be measured on a real phone.

**Decided 2026-10-23: B.** Measured on the emulator (Pixel 9 Pro XL, `SearchIndex.build` right after the copy, timed
with a temporary hook since removed):

| | build the table | search "love lord" in all six columns |
|---|---|---|
| debug build, first normalizer (regex, `Normalizer` on every stanza) | 4.3–6.1 s | 87 ms (body only) |
| debug build, one-pass normalizer | 2.5–2.8 s | 87 ms (body only) |
| **release build**, one-pass normalizer | **1.2–1.3 s** | **99 ms**, 1,112 hymns |

The copied database grows from 22.9 MB to 41.2 MB. A real phone is slower than the emulator on this PC, perhaps 2–4×:
a few seconds once per update, in the background. Still to check on Lemuel's phone when the feature is built.

Most of the time was the normalizer; it is now one pass over the text (tags, `&nbsp;`/`&amp;`, lower case, letters/
marks/digits), and runs the Unicode accent removal only on text with Latin, Greek or Cyrillic letters (two thirds of
the lyrics are Chinese, Korean etc., which it would not change). `SearchText.norm` gives exactly what the Python
`norm()` gives on all 209,398 texts of the database (stanzas and hymn fields), checked on the PC.

**Found while testing:** removing accents also turns Russian **й** into **и** ("святой" → "святои"), because й is
и + a breve mark. Search still works (the typed words get the same treatment), but "и" also finds "й". Keep the marks
that make a letter of its own: й (and ё?) for Russian; ask whether ñ matters for Spanish. Decide in step 1, in all
three normalizers.
