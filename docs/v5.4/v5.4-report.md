## Update 2026-09-06: note-rendering bug fix, Victor's 06.09 corrections, v5.4.2

Victor tested v5.4.1 and confirmed SS336, SS276/NS1073, SS329, and NS342 are all working. He reported one new issue: End-notes render as part of a hyperlink whenever a hymn has both an End-note and a SoundCloud/YouTube link (SS-59, SS-62, SS-83, SS-196, SS-225, SS-233, SS-267, SS-285, SS-298, SS-305, SS-320), and SS-422's End-note (between two choruses) doesn't show at all.

1. ✅ **Root cause found and fixed — general note-rendering bug, not a data problem.** `LyricsArea.java`'s `displayLyrics()` only ever flushed a `"note"` stanza to its own view when it happened to be the *last* stanza in the hymn; a note anywhere else silently merged into whatever stanza followed it in the same rendered text buffer. When that following stanza was a SoundCloud/YouTube link, the merged block (note text + URL) got wrapped in a single `ClickableSpan`, so tapping it called `Uri.parse()` on garbage — exactly Victor's screenshot. The same bug, independent of Victor's data, was also live in existing hymn data (e.g. Japanese hymn **J180**, found by inspecting `sqlite/hymns.sql` directly — a mid-hymn instructional note between stanzas 4 and 5 was silently disappearing into stanza 5's view). Fixed by always flushing a note to its own full-width row immediately, and fixing a column-pairing bug this surfaced in `buildLyricViewAndAttach` (inserting a full-width row mid-hymn was desyncing the two-column layout for every subsequent stanza — caught via a J180 regression before the final fix). Also removed a duplicate trailing `<br/>` that made the vertical gap under a note look uneven vs. the gap above it.
2. ✅ **SS-422 root cause found — separate parsing bug.** Victor's End-note text is literally "[Coro final sube de nota]" (a musical instruction, containing the word "Coro" as prose, not a real chorus). `ProvisionSpanishSupplement.groovy`'s chorus-detection regex matched the word "Coro" *anywhere* in a line, not just at real `Coro:` headers, so this line was misclassified as an empty new stanza. Anchored the regex to the start of the line (verified against every real chorus header in the file — all 470+ start with "Coro"). Verified fix against SS422 directly; diffed the full `SS` range after re-provisioning and confirmed SS422 was the *only* hymn with a content change.
